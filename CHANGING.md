# Changing things later

Plain JavaScript modules, no build step: edit a file, commit, refresh. Run `npm test` after changes.

## Map
- `index.html`, `css/style.css` (original look), `css/lock.css` (sign-in, account tab)
- `js/app.js` — the original screens. They call `window.ninjaApi(method, "/api/...")` exactly like the old fetch calls.
- `js/api/*.js` — the old Flask routes with the same URLs and JSON (`leads`, `belts`, `active`, `rewards`, `settings`); `router.js` has `route(method, pattern, handler)`. They run against a local SQLite copy.
- `js/lib/*` — helpers ported from Python (CSV, schedule import, reward rules); `ninjas.js` = Ninja + family records and how every sheet links to them
- `js/pdf/*` — certificates and totem tags (pdf-lib). `data/certificate_layout.json` + `assets/certificate_template.pdf`
- `js/core/db.js` — local tables (`SCHEMA`), `DEFAULT_SETTINGS`, `MIGRATIONS`, SQL helpers, `SYNC_TABLES`
- `js/sync/` — `config.js` (your Supabase URL/key), `supabase.js` (login + table access), `sync.js` (send/receive changes), `login.js`, `account_panel.js`
- `supabase/schema.sql` — the shared tables and who may use them
- `tests/` — `test_routes.mjs` (API behaviour vs recorded output of the original Python app), `test_sync.mjs` (two people, conflicts, offline), `test_ninjas.mjs` (Ninja/family links, MyStudio import), `mock_supabase.mjs`, `e2e/` (browser, optional)

## Recipes
**Add a field to a table** (needs changes in 3 places, keep them identical):
1. `js/core/db.js`: add the column to `SCHEMA` **and** a function in `MIGRATIONS` (`ALTER TABLE ... ADD COLUMN ...`) — the local copy is rebuilt on every sign-in, so SCHEMA is what matters, but keep both.
2. Supabase SQL Editor: `alter table public.leads add column source text;` (same name and type family).
3. Use it in the route (`js/api/…`) and the screen (`js/app.js`). Sync picks up new columns automatically.
Do the Supabase step *before* publishing the new website files, or saves will fail.
**Add a route:** in the right `js/api/*.js` add `route("GET", "/api/thing/:id", ({params, query, body}) => ...)`; any route that changes data is synced automatically.
**Add a whole new table:** add it to `SCHEMA` and `SYNC_TABLES` (db.js) and create it in Supabase using the same pattern as `supabase/schema.sql` (identity id, `updated_at`, `deleted`, trigger, RLS policy, grants) — and add its name to the table list in that file's `do $$` loop. A table whose rows other tables point at should use a browser-made `uid text primary key` instead of an identity id (like `ninjas` / `families`, `pk: "uid"` in `SYNC_TABLES`): those are saved as insert-or-update, so the key never changes after it is made.
**New setting:** add to `DEFAULT_SETTINGS` in `db.js` (applies when the shared database has none).
**Add / remove a team member:** Supabase → Authentication → Users.
**Change the certificate:** replace `assets/certificate_template.pdf`, then `pip install pdfplumber` and `python3 tools/extract_layout.py`; adjust `js/pdf/certificates.js` if positions change.
**Totem tag look:** `js/pdf/totem_tags.js`.
**How the data fits together:** one row in `ninjas` per child (name, belt, `family_uid`) and one row in `families` per paying customer / parent (name, email, phone). Every other sheet has a `ninja_uid` column pointing at its child: `active_ninjas` (one row per weekly class), `belt_entries`, `receipts`, `jr_notes`, `leads`. The Ninja record is the truth for a child's name and belt; the copies on the other sheets are refreshed by `linkEverything()` in `js/lib/ninjas.js`, which the router runs before a request whenever anything changed (here or from a teammate). It also links rows that have no `ninja_uid` yet, by exact name (case/spacing ignored), and leads by name or by parent email/phone + first name. So renaming a Ninja renames them on every tab, and a lead shows "Enrolled" once that child has classes. A Ninja with no classes is simply not enrolled now; their record and history stay. uids are made from the name/email (`n-mia-lee`, `f-lee-x-com`), so two teammates creating the same record end up with one row.
**MyStudio schedule import** (Date, Time, Class name, Participant name, Customer name, Email address, Phone number — participant = the Ninja, customer = the parent): `parseClassSchedule` in `js/lib/schedule_import.js` reads it; the review-then-apply routes are in `js/api/active.js` (`/import`, `/import/confirm`). Children are matched to Ninjas by name, or by parent email/phone + first name (so "Daniel K" on the roster and "DANIEL KINOSHI" in the file are the same child once his parent is saved). The review shows: new Ninjas (with parent, and the lead they came from), changes for Ninjas already here (new / missing classes, JR or AI marks, new parent details, optional rename), and Ninjas not in the file (their classes can be removed). A missing class is only pre-ticked for removal when the file has classes on that weekday. Nothing changes until the button is pressed.
**Belts from MyStudio:** any MyStudio CSV with a belt / rank column ("Rank", "Belt", "Current Rank", ... see `CLASS_HEADER_ALIASES` in `js/lib/schedule_import.js`) is compared with each Ninja's belt — either a column in the class export, or a list of names + ranks (`looksLikeRankList` / `parseRankList`), which can be imported on the Active Ninjas or the Belts tab. The rank text is read with `beltFromRank` (`js/lib/rewards.js`): only belts listed in Settings count. A higher belt is a belt-up: a Belts-tab row old → new is added (so Rewards follow) and the Ninja's belt changes; no belt yet = a starting-belt row (blank old belt, no rewards); a lower belt is offered unticked. Logic in `beltChange` / `applyBelt` in `js/api/active.js`.
**JR Ninjas:** a class whose MyStudio class name contains "JR" / "Junior" / "ScratchJr" gets `active_ninjas.is_jr` (`JR_CLASS_RE` in `js/lib/schedule_import.js`). Notes on what each JR Ninja is working on are rows in `jr_notes` (name, note, author, `ninja_uid`), linked to the Ninja; routes in `js/api/jr.js`, screen is the "JR Ninjas" view on the Active Ninjas tab.
**Current belt:** the Ninja's belt on the Active Ninjas tab (`ninjas.belt`, copied onto each of their classes as `active_ninjas.belt`); if that is blank, the "new belt" of their latest row in the Belts tab. The Belts tab is the belt-up log: when a Ninja's latest Belts-tab entry has a higher belt than theirs (or they have none), their belt moves up to it — never down (`fillMissingBelts`, run when a Belts entry is added and when the Active Ninjas tab loads). Raising a belt in the Active Ninjas edit window adds the belt-up to the Belts tab (unless "record as a belt-up" is unticked, for fixing mistakes); a first belt is saved as a starting-belt row. The "Fill in belts" window (`POST /api/ninjas/belts`) is for Ninjas with no belt, since MyStudio's export has none. Names match ignoring case/spacing or on first + last name, and a name that fits several Ninjas is asked about once (answers kept in the `belt_name_links` setting). All in `js/lib/belt_match.js`. A Belts-tab row with a blank old belt records a starting belt without creating any rewards.
**How often it syncs:** `intervalMs` in `js/main.js` (default 15 s). **Auto sign-out choices:** `js/core/autolock.js`.
**Update SQLite:** `python3 tools/fetch_sqljs_from_npm.py <version>` (checks npm's integrity hash).
**Roles (e.g. read-only members):** not built. It would be done with a `profiles` table + stricter policies in `schema.sql`.
**Upgrading the shared database:** when a version adds tables/columns, paste ALL of `supabase/schema.sql` into Supabase → SQL Editor and Run it (safe to run again; it only adds what is missing) **before** pushing the new website files. If the website goes first, sign-in shows "The shared database needs a one-time upgrade…".
